# mini-RPC项目面试话术

## 1. 这个项目是做什么的？

这是一个自己实现的简化版 RPC 框架，核心目标不是做复杂业务，而是跑通“本地方法调用 -> 网络请求 -> 服务端执行 -> 响应返回”的完整链路。项目主要覆盖了 JDK 动态代理、Netty 通信、编解码、服务端反射调用、请求响应配对、连接复用和超时治理。

## 2. 为什么要做 RPC，而不是直接本地调用？

本地调用只适用于同一个进程内的方法执行，但真实后端系统通常会拆成多个服务，部署在不同进程甚至不同机器上，这时就必须通过网络通信完成调用。RPC 的价值是把远程调用包装成接近本地方法调用的体验，降低业务开发复杂度。

## 3. 客户端为什么调用 `helloService.hello(...)` 时会先进入代理，而不是实现类？

因为客户端拿到的 `helloService` 不是 `HelloServiceImpl`，而是 JDK 动态代理生成的代理对象。代理对象实现了同一个接口，所以调用形式不变，但真正执行时会先进入 `InvocationHandler`，由代理层把接口名、方法名、参数类型和参数值组装成 `RpcRequest` 再发给服务端。

## 4. 动态代理在这个项目里的核心作用是什么？

核心作用是把一次本地接口调用转换成一次远程调用请求。业务方只需要像调用普通方法一样写代码，代理层会负责提取方法元信息、封装请求对象、发送请求、接收响应并返回结果。

## 5. `RpcRequest` 为什么要有 `interfaceName`、`methodName`、`parameterTypes`、`args`？

因为服务端要靠这几个字段把请求重新还原成一次本地方法执行。`interfaceName` 用来定位服务实例，`methodName` 和 `parameterTypes` 用来精确定位方法，`args` 是实际参数。只有这些信息齐全，服务端才能正确反射调用目标方法。

## 6. 为什么注册服务时要用接口名做 key，而不是实现类名？

因为 RPC 对外暴露的是服务契约，不是内部实现细节。客户端请求里带的是接口名，服务端也应该按接口名查找实现对象，这样才能解耦调用方和实现类，后续替换实现、扩容多实例时也更自然。

## 7. 服务端是怎么从网络中收到请求的？

不是手写 `socket.read()`，而是 Netty 底层读到 TCP 字节后，沿着服务端 pipeline 触发入站事件。请求会先经过 `LengthFieldBasedFrameDecoder` 拆帧，再经过 `RpcMessageDecoder` 反序列化成 `RpcRequest`，最后回调到 `RpcServerRequestHandler#channelRead0(...)`，这里就是服务端真正拿到请求对象的位置。

## 8. `channelRead0(...)` 为什么会自动触发？

因为 handler 被注册进了 `ChannelPipeline`，Netty 在底层收到网络数据后会自动传播入站事件。消息沿着 pipeline 逐个处理，当消息类型匹配到 `SimpleChannelInboundHandler<T>` 的泛型 `T` 时，Netty 就会自动回调对应的 `channelRead0(...)`。

## 9. 服务端收到请求后是怎么执行业务方法的？

服务端先根据 `interfaceName` 从 `ServiceRegistry` 找到服务实现对象，再根据 `methodName + parameterTypes` 通过反射定位具体方法，最后使用 `method.invoke(service, args)` 执行业务逻辑，并把返回值封装进 `RpcResponse`。

## 10. 客户端为什么要先 `pendingRequests.put(requestId, future)`，再发送请求？

为了避免竞态问题。如果先发请求再入表，极端情况下服务端响应可能已经回来了，但客户端映射还没建立，响应就无法找到对应 future。先入表再发送，才能保证响应回来时一定有地方可查。

## 11. Day3 为什么要引入 `requestId -> CompletableFuture` 映射？

这是为了支持并发场景下的请求响应精准配对。多个请求可以共用一条连接并发发送，响应回来时不一定按发送顺序返回，所以必须通过唯一的 `requestId` 找到对应请求的 future，再把结果交还给正确的调用线程。

## 12. 客户端收到响应后，是怎么唤醒最初发起调用的线程的？

调用线程在 `future.get(...)` 处阻塞等待结果。响应回来后，客户端 Netty I/O 线程会在 `RpcClientResponseHandler` 中根据 `requestId` 找到对应 future，并执行 `future.complete(response)`。一旦 future 被完成，原来阻塞的调用线程就会被唤醒并继续返回结果。

## 13. 为什么 `pendingRequests` 必须用 `ConcurrentHashMap`？

因为它会被多个线程并发访问。业务线程会在发送请求时 `put`，客户端 I/O 线程会在收到响应时 `remove`，断连或异常时还会遍历并批量清理。如果用普通 `HashMap`，会有线程安全和数据一致性问题。

## 14. Day3 为什么要做连接复用？

如果每次请求都重新建连，会有 TCP 建连开销，吞吐和延迟都会更差。连接复用的好处是减少频繁建连成本，让多个请求可以复用同一条活跃连接，提高整体通信效率。

## 15. 第二次请求为什么不会重新建连？

因为 `RpcClient#ensureConnected()` 会先检查当前 `channel` 是否存在且处于活跃状态。如果是，就直接返回已有连接；只有连接为空或失效时，才会进入加锁建连逻辑。

## 16. `volatile channel` 的作用是什么？为什么还需要加锁？

`volatile` 用来保证 `channel` 的可见性，也就是一个线程更新后其他线程能看到最新值。但它不能保证“检查再建连”这种复合操作的原子性，所以还需要 `synchronized (connectLock)` 避免多个线程同时重复建连。

## 17. 为什么超时、断连、异常时一定要清理 `pendingRequests`？

因为 `pendingRequests` 里保存的是未完成请求的上下文。如果请求已经超时或连接已经断开，但 future 还留在 map 里，就会造成内存泄漏和请求悬挂。Day3 里成功、超时、异常、断连路径都会做清理，确保请求生命周期能正确结束。

## 18. `failAllPending(...)` 的意义是什么？

当连接断开或 handler 异常时，所有还在等待中的请求都不可能正常完成了。`failAllPending(...)` 会把这些 future 批量异常完成，让调用线程尽快失败返回，而不是永久卡死在 `future.get(...)` 上。

## 19. Day3 相比前两天最核心的进步是什么？

Day1 主要是跑通最基本的 RPC 闭环，Day2 主要是把 Socket 升级成 Netty，Day3 则开始补齐工程可用性，重点解决了连接复用、请求响应精准配对、并发安全、超时控制和断连清理这些真实场景下必须面对的问题。

## 20. 这个项目里 `RpcClient` 和 `RpcServer` 的职责有什么区别？

`RpcClient` 站在消费端视角，负责发送请求、维护连接、等待响应、做超时和异常治理；`RpcServer` 站在提供端视角，负责监听端口、接收请求、定位服务实现、执行方法并返回响应。前者偏调用控制，后者偏请求处理。

## 21. Day3 最能体现工程思维的设计点是什么？

最核心的是请求生命周期管理。具体包括：发送前先挂 future、用 `requestId` 精准配对、复用连接避免重复建连、用并发安全容器维护 pending 请求、在超时和断连时及时清理上下文。这些设计让项目从“能跑 demo”提升到“具备基础工程可用性”。

## 22. 如果面试官问这个项目还有哪些明显可以继续演进的方向，怎么答？

可以继续往服务注册与发现、负载均衡、失败重试、序列化协议优化、心跳保活、线程池隔离、链路追踪等方向演进。也就是从单机直连 demo，逐步走向更接近真实分布式 RPC 框架的形态。

## 23. Day4 为什么要从固定 IP 直连升级成服务发现？

因为固定地址只适合 demo，一旦服务实例扩容、迁移或下线，客户端代码就必须跟着改，完全不具备扩展性。服务发现的作用是把“服务在哪”从业务代码里抽离出去，让客户端先按服务名查实例，再决定连哪台机器。

## 24. 这个项目里的 Day4 注册中心是怎么工作的？

Day4 先实现了一个本地文件注册中心作为最小可运行版本。服务端启动时把 `serviceName -> host:port` 写入注册文件，客户端发起调用时按服务名读取实例列表，再基于负载均衡选出目标实例。这样可以先把注册发现主链路跑通，后续再平滑替换成 Zookeeper。

## 25. Day4 的负载均衡和失败重试是怎么做的？

客户端先从注册中心发现多个实例，再通过负载均衡策略选出一个目标实例并复用连接。若本次实例连接或发送失败，客户端会在最小重试次数内切换到其他未尝试实例再发起调用，从而提升可用性。

## 26. Day5 到 Day6 的真正核心变化是什么？

Day5 的服务发现更像“每次调用前都去 ZooKeeper 现查实例列表”，Day6 则把它升级成“首次拉取 + JVM 本地缓存 + watcher 自动刷新”。也就是说，Day6 的关键不是单纯用了 CuratorCache，而是把客户端服务发现模式从被动查询升级成了缓存优先和动态同步。

## 27. Day6 的本地缓存里存的到底是什么？

缓存里存的不是 `HelloServiceImpl` 这种业务对象，也不是 Netty 连接对象，而是 `serviceName -> List<ServiceInstance>`。它本质上表示“某个服务当前有哪些可用实例地址”，例如 `HelloService -> [127.0.0.1:9000, 127.0.0.1:9001]`。

## 28. 为什么一个服务会有多个实例？

服务是逻辑能力名，实例是这个能力当前在哪个地址上的运行副本。一个服务有多个实例是为了分摊流量、提高可用性并支持负载均衡。客户端真正调用的不是抽象的服务名，而是服务名对应的某一个具体实例地址。

## 29. 为什么 `discover(serviceName)` 返回的是实例列表，而不是实现类对象？

因为客户端并不持有服务端 JVM 里的 `HelloServiceImpl` 对象，客户端真正需要知道的是“这个服务现在可以发往哪些 host:port”。所以注册中心返回的一定是实例地址列表，而不是实现类对象。

## 30. Day6 里 watcher 的作用到底是什么？

watcher 的作用不是替客户端发请求，而是持续维护 JVM 本地缓存。第一次 discover 时客户端会先拉取实例列表到本地；后续一旦 ZooKeeper 上的服务节点发生变化，watcher 就会触发重新拉取最新实例列表，并整体覆盖旧缓存。

## 31. 为什么 Day6 不是在 watcher 事件里手工 add/remove 缓存，而是整体重刷？

因为整体重刷更简单、更稳，也更适合教学项目。这样不用在本地推演事件顺序和边界情况，缓存始终以 ZooKeeper 当前真实结果为准。代价是刷新时多一次完整读取，但换来了更低的实现复杂度和更容易讲清楚的逻辑。

## 32. 为什么 `discover(...)` 返回的是缓存副本，而不是直接返回内部缓存？

因为内部缓存是注册中心自己维护的真实状态。如果直接把内部列表原样返回，外部代码做 `clear()`、`remove()` 等操作时就可能把内部缓存改坏。返回副本的目的是保护内部缓存不被调用方误修改。

## 33. 为什么同一个服务已经有 watcher 了，还要 `watcher.close()`？

这里关闭的不是原来已经在 `serviceWatchers` 里的正式 watcher，而是“当前新建出来但没被采用的重复 watcher”。并发场景下，多个线程第一次 discover 同一个服务时，可能都创建 watcher；最终只保留第一个正式注册成功的 watcher，其他重复副本要立即关闭，避免资源浪费和重复监听。

## 34. 为什么这里用接口类型 `RegistryCenter` 调 `discover(...)`，而不是直接写成 `ZookeeperRegistryCenter`？

这是面向接口编程。`RpcClient` 只依赖“注册中心能 discover 实例”这个抽象能力，而不依赖具体是文件实现还是 ZooKeeper 实现。这样 Day4 的 `FileRegistryCenter`、Day5/Day6 的 `ZookeeperRegistryCenter` 都能无缝切换，上层调用代码基本不用改。

## 35. JVM 是怎么知道该调用哪个 `discover()` 实现的？

编译时只检查接口 `RegistryCenter` 是否声明了 `discover(...)`；运行时真正执行哪个实现，由变量里实际引用的对象决定。比如 `RegistryCenter registryCenter = new ZookeeperRegistryCenter()`，那运行时调用的就是 `ZookeeperRegistryCenter#discover(...)`。这就是多态。
