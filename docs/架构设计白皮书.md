# Mini RPC 架构设计白皮书

## 1. 文档定位

本白皮书只负责回答四件事：

- 为什么要做 Mini RPC
- 系统整体怎么工作
- 关键技术为什么这么选
- 之后如何平滑演进

不负责命令行部署细节、不负责故障案例清单，这两部分分别由《部署指南》《故障排查及解决文档》负责。

## 2. 问题背景与目标

### 2.1 问题背景

服务拆分后，调用从“进程内方法调用”变为“跨网络远程调用”。如果直接手写 HTTP 请求，会产生大量重复代码与治理成本：

- 业务代码侵入网络细节
- 服务地址写死，扩缩容困难
- 缺少统一超时、重试、负载均衡、容错能力

### 2.2 项目目标

Mini RPC 的目标是：让调用方保持“本地方法调用体验”，同时具备远程调用的基础设施能力。

## 3. 架构原则

- 最小闭环优先：先跑通一次最小调用，再增强治理能力
- 分层解耦优先：协议、传输、治理、业务职责明确
- 可替换优先：序列化、负载均衡等组件通过接口抽象
- 可演进优先：协议预留版本字段，兼容后续升级

## 4. 模块划分与职责

```text
mini-rpc/
  rpc-core
  rpc-client
  rpc-server
  rpc-registry
  rpc-demo
```

### 4.1 rpc-core（协议与编解码中枢）

职责：

- 定义 RpcRequest、RpcResponse
- 序列化与反序列化抽象
- 编码解码逻辑

没有它会怎样：  
客户端和服务端各写一套协议逻辑，耦合严重、维护成本高。

### 4.2 rpc-client（消费端调用入口）

职责：

- 动态代理拦截调用
- 发起远程请求
- 承载超时控制、重试与负载均衡入口

没有它会怎样：  
业务层需要自己写网络请求，调用体验差且重复代码多。

### 4.3 rpc-server（提供端执行入口）

职责：

- 服务暴露
- 请求路由到本地实现
- 响应封装与回传

没有它会怎样：  
服务处理路径分散，无法统一治理与扩展。

### 4.4 rpc-registry（服务注册与发现）

职责：

- 服务注册
- 服务发现
- 实例变更感知（后续）

没有它会怎样：  
地址硬编码，服务下线或扩容会直接影响可用性。

### 4.5 rpc-demo（验证与教学样例）

职责：

- 端到端联调演示
- 阶段性回归验证

没有它会怎样：  
每次改动都难以快速确认“是否跑通”。

## 5. 调用链路（端到端）

1. 业务代码调用接口方法  
2. 动态代理拦截调用，构建 RpcRequest  
3. 服务发现获取可用服务实例列表  
4. 负载均衡选出目标实例  
5. 客户端编码并通过 Netty 发送请求  
6. 服务端解码、反序列化并执行本地方法  
7. 封装 RpcResponse 返回客户端  
8. 客户端解码响应并返回结果或抛出异常

## 6. 关键技术选型与权衡

### 6.1 Netty

选择原因：

- 基于 NIO 的高并发事件驱动模型
- 线程模型成熟，吞吐与延迟表现稳定
- 编解码管线易扩展，适合 RPC 场景

权衡：

- 学习成本高于 BIO
- 但更贴近真实生产场景

### 6.2 动态代理

选择原因：

- 屏蔽网络细节，让调用方保留本地接口体验
- 形成统一拦截点，便于接入日志、重试、链路追踪

权衡：

- 调试时调用链更抽象
- 但极大降低业务侵入

### 6.3 序列化

选择原因：

- 网络只传字节，必须对象与字节互转
- 统一协议可保证请求与响应可解析

权衡：

- 不同协议在性能、可读性、兼容性上取舍不同
- 初期优先简单可验证，后续按性能演进

### 6.4 注册中心 + 负载均衡 + 容错

选择原因：

- 注册中心解决“服务在哪”
- 负载均衡解决“请求打到谁”
- 容错解决“目标异常怎么办”

权衡：

- 复杂度提高
- 但这是分布式服务可用性的基本保障

## 7. 协议设计基线

请求与响应至少应包含：

- version
- requestId
- serviceName
- methodName
- parameterTypes
- args
- data
- error

设计要点：

- requestId 用于请求响应匹配
- version 用于协议兼容演进
- method + parameterTypes 用于方法重载定位

## 8. 可观测与排障基线

最小日志建议：

- 请求日志：requestId、服务名、方法名、耗时、结果
- 错误日志：网络错误、编解码错误、业务异常分层记录

最小排障路径：

1. 先分层定位（网络/协议/业务）  
2. 用 requestId 串联客户端和服务端日志  
3. 判断是实例不可达、解码失败还是业务异常

## 9. 演进路线

- Day1：多模块、协议模型、固定地址直连调用
- Day2-3：Netty 通信和编解码
- Day4：服务注册与发现 + 本地负载均衡
- Day5：真实注册中心（Zookeeper）
- Day6：实例缓存与监听
- Day7：容错机制

每阶段统一交付标准：

- 可运行：有最小可执行样例
- 可验证：有清晰成功判定
- 可讲述：能说明动机、方案、权衡、结果
