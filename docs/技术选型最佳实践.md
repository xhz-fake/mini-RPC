# Mini RPC 技术选型最佳实践

## 1. 文档目标

本文件只回答“为什么这么选”和“什么时候该换方案”。  
不展开部署命令、不堆故障细节，确保决策清晰、可复用。

## 2. 选型总览

- 网络通信：Netty
- 调用抽象：JDK 动态代理
- 协议模型：RpcRequest / RpcResponse
- 序列化策略：可替换接口 + 默认实现
- 服务治理：注册中心 + 负载均衡 + 容错
- 构建方式：Maven 多模块

## 3. 最佳实践清单

### 3.1 Netty 选型

推荐：

- 使用事件驱动模型处理高并发连接
- 把编解码作为独立处理器放入管线
- 业务线程与 IO 线程职责分离

避免：

- 在 IO 线程执行重计算或阻塞逻辑
- 把业务异常吞掉不记录 requestId

替代方案：

- 学习阶段可先用 BIO 验证链路
- 但生产思路优先 Netty/NIO

### 3.2 动态代理选型

推荐：

- 通过 InvocationHandler 统一拦截远程调用
- 代理层只做组装请求与调用转发，不写业务逻辑

避免：

- 业务代码直接依赖网络层对象
- 在代理中硬编码重试/超时策略

替代方案：

- CGLIB 可用于类代理
- 本项目接口代理场景优先 JDK 动态代理

### 3.3 序列化选型

推荐：

- 定义 Serializer 接口，按名称或枚举选择实现
- 协议字段保持稳定，先确保兼容性再追求极致性能

避免：

- 把序列化实现写死到业务流程
- 字段随意删改导致跨版本不兼容

替代方案：

- JSON：可读性好，性能一般
- Kryo/Protobuf：性能高，维护复杂度更高

### 3.4 注册中心选型

推荐：

- 服务实例注册时附带健康状态
- 客户端缓存服务列表并定期刷新

避免：

- 业务层自行维护服务地址
- 服务列表更新无版本或时间戳

替代方案：

- 学习阶段可本地内存注册中心
- 进阶可接入 Nacos/ZooKeeper/Etcd

### 3.5 负载均衡与容错选型

推荐：

- 默认轮询，便于验证与排查
- 容错从“超时 + 有限重试”起步
- 失败重试要配合幂等设计

避免：

- 无限重试导致雪崩
- 忽略下游失败率和超时指标

替代方案：

- 轮询、随机、一致性哈希按场景切换
- 熔断降级在 Day7 演进

## 4. 模块化最佳实践

- rpc-core 只放协议和通用能力，不依赖业务模块
- rpc-client 与 rpc-server 通过 core 协议对齐
- rpc-demo 仅演示，不承载核心实现
- 新增能力优先接口扩展，避免侵入式修改

## 5. 面试表达模板（技术选型版）

建议按“问题-方案-权衡-落地”回答：

1. 问题：服务拆分后调用复杂、治理困难  
2. 方案：Netty + 动态代理 + 可替换序列化 + 注册发现  
3. 权衡：复杂度上升，但性能、可维护性、可扩展性更好  
4. 落地：按 Day1~Day7 分阶段实现并可验证
